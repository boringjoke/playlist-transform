# 歌单清单转换工具总体开发计划

## 1. 文档信息

- 文档状态：初版，待用户确认
- 对应需求：`docs/需求文档.md`
- 当前阶段：阶段 0，需求与总体设计确认
- 计划目标：完成不登录音乐平台、只生成导入内容的 MVP

## 2. 技术路线结论

### 2.1 正式工程基线

依据当前 `AGENTS.md`，总体开发计划暂采用：

- 前端：Nuxt 4、Vue 3、TypeScript；
- 后端：Java 17、Spring Boot 4.1.1、Maven；
- 部署：前后端独立 Docker 镜像，前端最终由 Nginx 提供静态资源；
- 数据库：MVP 不引入；
- Redis、Session、消息队列：MVP 不引入；
- Python：不进入第一版生产链路，仅保留为后续 OCR 或算法实验选项。

此前讨论中的 Vue 3 + Vite 和 Java 21 属于通用技术建议。Nuxt 4 本身基于 Vue 3 和 Vite，但 Java 版本存在明确差异；编码前必须由用户确认是否调整现有工程基线。

### 2.2 架构原则

1. 第一版保持前后端分离的无状态单体结构。
2. 不为了未来能力预建数据库、缓存、登录和异步任务系统。
3. 文本解析采用确定性规则优先，不依赖大模型。
4. 平台差异通过导出适配器隔离。
5. 解析结果明确区分“已识别”“信息不完整”“存在歧义”和“无效”。
6. 不调用非官方音乐接口，不获取音频、歌词、封面或会员播放信息。
7. 用户原始歌单默认只在当前请求和浏览器本地草稿中存在。

## 4. 前端设计

### 4.1 技术组成

- Nuxt 4；
- Vue 3 Composition API；
- TypeScript 严格模式；
- Pinia，仅在跨页面状态确有需要时使用；
- Element Plus，用于表单、表格、标签、提示和弹窗；
- Nuxt 内置路由；
- `vue-tsc` / Nuxt 类型检查；
- Vitest，用于核心前端工具函数；
- Playwright，用于核心流程定向端到端验证。

### 4.2 渲染策略

MVP 的工具页以客户端交互为主。Nuxt 应使用适合静态部署的策略：

- 产品介绍、隐私说明和使用说明可预渲染；
- 输入、确认和导出流程在客户端执行；
- 不依赖 Nuxt Server 保存用户状态；
- 构建方式和 Nginx 静态资源路径在部署阶段专项确认。

### 4.3 页面与路由建议

| 路由 | 页面 | 说明 |
| --- | --- | --- |
| `/` | 首页与输入页 | 产品说明、文本输入、本地草稿 |
| `/review` | 解析确认页 | 编辑、删除、排序、去重、问题筛选 |
| `/export` | 导出页 | 平台选择、预览、复制、TXT 下载 |
| `/privacy` | 隐私说明 | 数据处理、本地草稿和清除方式 |
| `/guide` | 使用说明 | 平台导入步骤和限制说明 |

前端不能仅依赖路由内存传递结果。刷新 `/review` 或 `/export` 时，应从受版本控制的浏览器本地草稿结构恢复；无法恢复时返回首页并说明原因。

### 4.4 前端状态结构

~~~ts
interface PlaylistDraft {
  schemaVersion: number
  sourceText: string
  tracks: ParsedTrack[]
  selectedProvider?: 'QQ_MUSIC' | 'NETEASE_MUSIC'
  updatedTime: string
}
~~~

本地草稿必须：

- 使用独立 storage key；
- 包含 schemaVersion；
- 支持显式清除；
- 结构不兼容时安全丢弃，不尝试错误迁移；
- 不存储任何音乐平台登录凭据。

### 4.5 大列表交互

第一版验收容量为 500 首。实现时应：

- 避免每次输入都重建整个列表；
- 对筛选、排序和去重使用稳定 clientId；
- 拖动后保持顺序一致；
- 若普通列表渲染出现明显卡顿，再引入虚拟列表，不提前增加复杂度。

## 5. 后端设计

### 5.1 技术组成

- Java 17；
- Spring Boot 4.1.1；
- Spring MVC；
- Spring Validation；
- Jackson；
- Apache Commons Text，仅用于必要的字符串相似度计算；
- Caffeine，仅在出现可复用的只读规则数据后启用；
- Spring Boot Actuator，仅暴露必要健康检查；
- JUnit 5；
- MockMvc；
- Maven。

MVP 不使用 WebFlux、JPA、MyBatis Plus、Flyway、MySQL、Redis、Spring Session、Kafka 或 RabbitMQ。

### 5.2 模块划分

~~~text
backend/src/main/java/.../
├── common/
│   ├── exception/
│   └── response/
├── playlist/
│   ├── controller/
│   ├── application/
│   ├── domain/
│   ├── parser/
│   ├── exporter/
│   └── dto/
└── config/
~~~

职责：

- `controller`：参数接收、校验和响应，不编写解析规则；
- `application`：编排解析和导出用例；
- `domain`：平台无关的歌曲、状态和警告模型；
- `parser`：标准化、分行、字段解析、置信度和去重判断；
- `exporter`：不同平台的导出格式；
- `dto`：接口请求和响应对象，字段补充中文注释；
- `common/exception`：统一异常；
- `common/response`：统一响应。

### 5.3 核心接口

遵循项目约定，接口路径使用驼峰，不使用短横线或下划线。

#### 解析文本

~~~text
POST /api/playlist/parseText
~~~

请求：

~~~json
{
  "text": "1、龙卷风 周杰伦\n2、夜曲"
}
~~~

响应业务数据：

~~~json
{
  "tracks": [
    {
      "clientId": "01...",
      "sourceIndex": 1,
      "rawText": "1、龙卷风 周杰伦",
      "title": "龙卷风",
      "artists": ["周杰伦"],
      "version": null,
      "status": "PARSED",
      "confidence": 0.98,
      "warnings": []
    }
  ],
  "summary": {
    "total": 2,
    "parsed": 1,
    "incomplete": 1,
    "ambiguous": 0,
    "duplicate": 0,
    "invalid": 0
  }
}
~~~

#### 生成导出内容

~~~text
POST /api/playlist/exportText
~~~

请求：

~~~json
{
  "provider": "QQ_MUSIC",
  "includeIncomplete": true,
  "tracks": [
    {
      "clientId": "01...",
      "title": "龙卷风",
      "artists": ["周杰伦"],
      "version": null
    }
  ]
}
~~~

响应业务数据：

~~~json
{
  "provider": "QQ_MUSIC",
  "trackCount": 1,
  "content": "龙卷风 - 周杰伦",
  "warnings": []
}
~~~

TXT 下载优先由前端根据导出响应生成 Blob，避免新增专用下载接口。

### 5.4 解析流水线

~~~text
请求大小校验
  → 换行标准化
  → 非空行拆分
  → Unicode NFKC
  → 行首序号识别
  → 明确分隔符解析
  → 版本标记识别
  → 单空格歧义判断
  → 字段清理
  → 状态与置信度计算
  → 疑似重复标记
  → 汇总结果
~~~

解析顺序必须稳定。同一输入在相同规则版本下应产生相同结果。

### 5.5 解析规则版本

建议为解析结果增加内部规则版本，例如 `parserRuleVersion`，用于：

- 定位规则升级后的差异；
- 固定测试样本预期；
- 判断旧草稿是否需要重新解析。

规则版本属于技术字段，不应被宣传为歌曲准确性保证。

### 5.6 导出适配器

~~~java
public interface PlaylistTextExporter {
    MusicProvider provider();
    ExportResult export(ExportCommand command);
}
~~~

第一版至少实现：

- `QqMusicTextExporter`；
- `NeteaseMusicTextExporter`。

核心模型不得包含 QQ 或网易云平台歌曲 ID。平台格式变化时只调整对应导出器和测试。

## 6. Python 使用策略

Python 不进入 MVP 生产服务。允许在独立的开发工具目录用于：

- 生成解析测试样本；
- 比较 RapidFuzz 等算法效果；
- 统计规则准确率；
- 后续 OCR 可行性验证。

如果未来引入 Python 服务，必须先补充专项设计，明确：

- 为什么 Java 无法合理完成；
- 服务边界和接口；
- Docker、健康检查和资源限制；
- 用户文本是否离开主服务；
- 超时、回退和隐私处理。

## 7. 安全与隐私设计

### 7.1 输入安全

- 请求体限制为与 500 首验收容量匹配的大小；最终字节值在实现阶段通过样本确定并写入配置。
- 限制非空行数和单行长度。
- 拒绝二进制内容和异常编码。
- 不接受任意 URL 抓取。
- 后端不执行用户文本中的任何表达式、HTML 或命令。

### 7.2 日志

- 不记录完整原始文本、完整解析结果或完整导出文本。
- 可记录请求 ID、条目数、耗时、规则版本和错误类型。
- 异常堆栈不得附带请求正文。
- 前端错误上报不得携带歌单正文。

### 7.3 浏览器安全

- 不使用 `v-html` 渲染歌曲内容。
- 设置合理的 CSP、Referrer-Policy 和 Permissions-Policy。
- 本地草稿不包含账号信息。
- 清除草稿后立即移除 storage key。

### 7.4 平台与版权边界

- 不抓取音频、歌词、封面、播放地址和会员资源。
- 不调用逆向接口。
- 不伪装为 QQ 音乐或网易云音乐官方产品。
- 平台名称仅用于说明兼容目标。
- 导入指南只描述用户在官方客户端中可见、经实测的正常功能。

## 8. 配置设计

### 8.1 后端

配置分为：

- `application.yaml`：公共配置；
- `application-dev.yaml`：开发环境；
- `application-prod.yaml`：生产环境。

建议配置项：

- 最大请求字节数；
- 最大歌曲条目数；
- 最大单行长度；
- 解析规则版本；
- 允许的前端来源；
- Actuator 暴露范围。

所有生产地址和敏感值通过环境变量提供，不提供非空硬编码默认值。

### 8.2 前端

建议配置项：

- API base URL；
- 应用 base URL；
- 草稿 storage key 和 schemaVersion；
- 隐私与使用说明版本；
- 是否展示某个平台导出入口。

平台导出入口应可配置关闭，以便兼容性失效时停止误导用户。

## 10. 部署设计

### 10.1 镜像

- 前端使用 Node 多阶段构建，最终由 Nginx 提供静态内容；
- 后端使用 JDK 构建和 JRE 运行的多阶段 Dockerfile；
- 项目根目录作为构建上下文；
- 使用不可变版本 Tag；
- 前后端独立镜像和独立发布；
- MVP 无数据库和 Redis 容器。

### 10.2 网络

- 公共 Gateway 负责 80、443；
- 前后端默认使用 `expose`，不直接映射宿主机端口；
- 前端通过同源 `/api/` 反向代理到后端；
- 发布前核对域名或 IP 路径前缀；
- 修改共享 Gateway 前执行 `nginx -t` 并验证其他项目。

### 10.3 健康检查

- 后端仅开放必要的 Actuator health；
- 前端检查静态首页；
- 容器健康后再切换或确认发布；
- 发布和服务器操作必须另行获得用户授权。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 单空格无法可靠区分歌名和歌手 | 错误拆分 | 保守解析、降低置信度、要求用户确认 |
| 只有歌名时官方导入匹配错误 | 导入错误版本 | 明确提示并鼓励补充歌手 |
| 平台导入格式变化 | 导出失效 | 独立导出器、入口开关、发布前和周期性人工验证 |
| 网易云不支持纯文本导入 | 无法兑现文案 | 不展示“官方可导入”，调整为标准化文本或推迟平台 |
| 用户误以为本站是官方产品 | 商标与信任风险 | 中性命名、无官方 Logo、明确非官方说明 |
| 日志或分析服务泄露歌单 | 隐私风险 | 不记录正文、不把正文发送给第三方分析服务 |
| 为未来能力过度设计 | 延期和维护成本 | MVP 无数据库、无 Redis、无 MQ、无 Python 服务 |
| 500 首页面卡顿 | 体验下降 | 稳定 key、减少重渲染，必要时再使用虚拟列表 |

## 13. 后续扩展门槛

新增以下能力前必须先补充需求和专项设计：

- 公开歌单链接解析；
- 平台搜索和歌曲候选匹配；
- 会员播放范围；
- 收藏数、点赞数和评论数；
- 直接创建平台歌单；
- 用户账号和历史记录；
- 数据库、Redis 和 Session；
- OCR 和 Python 服务；
- PWA 系统分享、原生 App 或桌面客户端。

专项设计至少说明数据来源授权、字段含义、失败状态、缓存期限、限流、隐私、回退和验收样本。

1. 用户确认 `docs/需求文档.md` 的 MVP 范围。
