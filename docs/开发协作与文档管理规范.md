# 开发协作与文档管理规范

## 1. 目的

本文档定义项目开发过程中需求文档、总体开发计划、开发进度和代码之间的职责边界，并规定 agent 从接手任务到最终交付的完整执行流程。

本文档适用于：

- 新功能开发；
- 已有功能调整；
- 数据源、解析策略和监控链路开发；
- 前端页面和交互调整；
- Docker、Nginx、生产配置和发布准备；
- 缺陷诊断、验证和用户验收。

本文档不替代 AGENTS.md。AGENTS.md 保存长期有效的强制规则，本文档保存详细流程和模板。

## 2. 文档层级和职责

### 2.1 AGENTS.md

AGENTS.md 记录：

- 工程结构；
- 代码和接口约定；
- 数据库和安全边界；
- 禁止事项；
- 长期有效的测试、发布和文档规则；
- 本文档的引用。

AGENTS.md 不记录：

- 当前阶段具体状态；
- 临时版本号；
- 一次性故障；
- 尚未确认的方案；
- 某次发布的实际结果。

### 2.2 需求文档

需求文档记录已经确认的产品和业务要求：

- 页面和功能范围；
- 字段和接口；
- 用户角色、权限和状态；
- 交互要求；
- 业务约束；
- 验收标准；
- 明确排除的范围。

需求文档不能用来记录某次实际代码修改结果。

### 2.3 总体开发计划

总体开发计划记录：

- 阶段划分；
- 阶段目标；
- 技术路线；
- 模块依赖；
- 实施顺序；
- 已确认的详细设计；
- 阶段验收策略。

总体开发计划应描述将要完成什么以及为什么这样安排，不替代开发进度记录。

### 2.4 开发进度

开发进度记录项目真实状态：

- 已实现什么；
- 实际执行了什么验证；
- 用户验证了什么；
- 哪些内容未执行；
- 仍有哪些问题、冲突和风险；
- 下一步计划是什么。

开发进度必须区分计划、代码已完成、agent 已验证和用户已验证，不得把计划写成完成结果。

### 2.5 专项设计文档

数据源、接口、解析、部署、权限或复杂交互等详细设计，应放在对应专项文档中，不要只写在 Prompt、聊天记录或代码注释中。

## 3. 文档阅读顺序

开始任务前完整阅读：

1. AGENTS.md；
2. docs/需求文档.md；
3. docs/总体开发计划.md；
4. docs/开发进度.md；
5. 当前任务相关的专项设计文档；
6. 必要时阅读现有配置、测试和参考项目。

如果项目文档名称不同，应先定位等价文档并向用户说明。

阅读时必须重点确认：

- 当前阶段；
- 上一阶段的已完成范围；
- 用户已经验证的内容；
- 必须保留的已有改动；
- 当前明确排除的范围；
- 当前待办和验收条件；
- 是否存在需求、文档和代码冲突。

## 4. 文档优先级和冲突处理

处理优先级：

1. 用户最新明确确认；
2. 最新确认的需求和专项设计；
3. 总体开发计划；
4. 开发进度中的实际状态；
5. 现有代码和配置；
6. 历史文档、示例代码和参考项目。

这不是允许自行覆盖冲突的顺序。发现冲突时应：

1. 记录冲突双方；
2. 说明冲突涉及的页面、字段、接口、状态、数据或部署行为；
3. 说明可能影响；
4. 提出需要补充或确认的文档计划；
5. 暂停编码和外部变更，等待用户决策。

文档缺少当前阶段设计时，不能通过“合理推测”新增业务。应先补充需求或专项设计。

## 5. 阶段执行流程

### 阶段一：完整阅读文档

完成指定文档阅读后，整理：

- 当前阶段名称；
- 当前总体状态；
- 已完成内容；
- 必须保留内容；
- 本阶段目标；
- 文档依据；
- 明确排除项；
- 未解决冲突和风险。

### 阶段二：只读检查工作区

检查范围包括：

- 工作区状态；
- 项目目录；
- 现有代码；
- 配置文件；
- 测试文件；
- 数据库迁移；
- Dockerfile、Compose、Nginx 和脚本；
- 开发进度和专项文档；
- Figma Make 参考项目是否仅被读取而未修改。

只读检查阶段不执行：

- 编码修改；
- 删除、重置和覆盖；
- 数据库写入；
- 服务器部署；
- 镜像推送；
- 证书上传；
- 公共 Gateway 重启；
- 发送外部消息。

### 阶段三：判断当前待办

根据最新文档和只读检查结果，判断：

- 当前阶段是否仍然有效；
- 上一阶段是否真正完成；
- 待办是否已经在文档中确认；
- 现有代码是否已经部分实现；
- 是否需要先修改文档；
- 是否存在会改变范围的设计选择。

如果待办不在文档确认范围内，先停止并提出文档补充计划。

### 阶段四：开发前汇报

编码前必须向用户汇报以下内容：

#### 当前阶段和现状

说明当前处于哪个开发阶段，以及代码、配置、测试和文档的真实状态。

#### 已完成内容及必须保留的改动

列出已经完成的功能、用户验证结果和不能被覆盖的改动。

#### 准备检查或调整的目录

只列出本阶段涉及的目录和文件范围，并说明哪些目录只读。

#### 文档设计依据

明确引用需求文档、总体开发计划、专项设计和开发进度中的具体依据。

#### 实现或验证计划

按顺序说明准备实现、检查和验证的内容。

#### 验证方案

说明后端、前端、接口、浏览器、Docker、Nginx 或用户手工验证的范围。

#### 潜在冲突和风险

说明文档冲突、数据源变化、兼容性、部署中断、数据库迁移和回滚风险。

### 阶段五：等待确认

默认等待用户确认后再：

- 编码；
- 修改项目文件；
- 修改数据库迁移；
- 运行可能产生构建产物的验证；
- 修改 Docker、Nginx 和生产配置；
- 执行服务器或镜像操作；
- 扩展已确认的业务范围。

用户确认的范围必须记录在后续开发进度中。

### 阶段六：实现

实现时必须：

- 只实现文档已经确认的范围；
- 优先保留用户已有改动；
- 不擅自重命名包、接口、字段、目录和组件；
- 不擅自增加表结构、权限、业务状态或演示数据；
- 新增实体时同步更新 Entity、Mapper interface、Mapper XML 和 Repository；
- 复杂 SQL 写入 Mapper XML；
- 后端对象参数和响应字段补充中文注释；
- 代码注释优先使用中文；
- 生产密码和密钥只从环境变量读取。

### 阶段七：必要验证

验证范围根据风险最小化原则确定，不默认运行完整测试套件。

后端改动通常执行：

- Maven 编译；
- 受影响模块定向测试；
- 必要的数据库、Redis、Session、Flyway 或数据源验证。

前端改动通常执行：

- 类型检查；
- 生产构建；
- 受影响页面或路由的定向验证；
- 必要的桌面端、移动端、SSE 和静态资源验证。

部署改动通常执行：

- Compose config --quiet；
- Dockerfile 静态检查和目标平台检查；
- 镜像运行时检查；
- 容器启动、healthcheck、日志和网络验证；
- Nginx nginx -t；
- 域名/IP 路由和已有项目回归验证。

验证必须记录：

- 命令；
- 执行结果；
- 未执行的验证；
- 未执行原因；
- 是否需要用户手工验证。

### 阶段八：更新开发进度

每完成一个阶段，更新 docs/开发进度.md。建议格式：

~~~markdown
### X.Y 阶段名称（状态）

1. 实现结果：说明实际完成的代码、配置或文档。
2. 验证结果：说明 agent 实际执行的命令和结果。
3. 用户验证结果：说明用户实际确认或未确认的内容。
4. 未解决问题或冲突：列出剩余问题、文档缺口、环境限制和风险。
5. 下一步计划：只写下一阶段已经确认或待确认的计划。
~~~

状态必须明确区分：

- 已完成；
- 已实现待验证；
- 本地验证完成待用户验证；
- 待服务器验证；
- 暂停；
- 存在冲突。

不要删除历史进度，不要把一次性临时日志替代阶段总结。

### 阶段九：最终交付汇报

最终汇报必须包含：

1. 修改文件；
2. 未修改但必须保留的文件或模块；
3. 实现结果；
4. 验证命令和结果；
5. 用户已验证结果；
6. 未执行的验证及原因；
7. 遗留问题、冲突和风险；
8. 下一步建议或发布前置条件。

如果任务没有实际修改文件，也应明确说明仅完成只读检查或分析。

## 6. 发布和外部变更门槛

发布准备和实际发布必须分开：

- 发布准备：检查 Dockerfile、Compose、Nginx、证书目录、网络、镜像地址和命令。
- 实际发布：构建镜像、推送镜像、上传文件、登录服务器、拉取镜像、重建容器、修改 Gateway 和执行数据库操作。

除非用户明确授权，agent 默认只做发布准备和本地静态检查，不执行实际发布。

生产发布必须：

- 使用明确版本 Tag；
- 保留上一版本镜像；
- 服务器端 ACR 登录不写入脚本；
- 生产环境文件在版本更新前备份；
- 镜像拉取成功后再持久化新版本；
- 单服务更新使用 --no-deps；
- 不执行 docker compose down -v、docker system prune -a 或 docker volume prune；
- 共享 Gateway 更新前执行 nginx -t；
- 观察现有 IP 项目和其他域名项目；
- 回滚镜像前确认数据库迁移是否可逆。

离线镜像发布必须：

- 使用目标服务器架构构建；
- docker save 导出；
- 传输前后校验 SHA256；
- 服务器 docker load；
- 使用离线环境文件；
- 不执行 docker compose pull；
- 新容器健康后再考虑删除旧镜像。

## 7. 质量和事实记录

- 不把实时平台数据、公开接口结果和历史样本当作永久事实。
- 用户没有复现的问题可以记录为非阻塞风险，但不得擅自修改。
- 浏览器控制台中的第三方扩展错误应与项目自身错误区分。
- 验证结果必须基于实际执行，不得根据计划、代码阅读或推测填写“已通过”。
